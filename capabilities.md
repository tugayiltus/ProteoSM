# ProteoSM Capabilities

ProteoSM by ProteONE: ProteoSM is the product name, ProteONE the umbrella brand of all its products (ADR-0047).

## Overview

ITSM platform for one company (multiple departments and locations). Users: employees, IT staff, admins. Served as one HTTPS web application per company host: a Docker Compose stack (PostgreSQL, API with the SPA, Worker, nginx with TLS, nightly backup) on one on-premises server or cloud VM (ADR-0024); operator procedures in `docs/operations.md`. Out of scope: multi-tenancy, native mobile app, a full CMDB (CI classes, discovery, service dependency map), full problem management (problem SLA, problem emails, trend analysis; `proteosm.md` §2). Change management is available since Phase 8 (ADR-0031, ADR-0032); the maintenance calendar and change reports are Phase 9; ticket-change links and central search are Phase 10 (ADR-0033); light problem management is Phase 11 (ADR-0034); the service catalogue with service-asset links (light CMDB) is Phase 12 (ADR-0036).

## Configuration

Hosts: `ProteoSM.Api` and `ProteoSM.Worker`. Both fail at startup on an invalid `App` section and, outside Development, on an empty `Files:RootPath` or an empty or unwritable `DataProtection:KeysPath`; the API also fails on an invalid `Http:KnownProxyNetworks` entry; the Worker also fails at startup when `Email:Mode` is missing or unknown, or when the `EmailSender` lease is not longer than `Email:Smtp:TimeoutSeconds`.

| Key | Host | Meaning |
|---|---|---|
| `App:PublicBaseUrl` | API, Worker | Absolute `http`/`https` URL used to build links in email (`ticketUrl`). Empty or relative fails startup. Development: `http://proteosm.localhost:5310`. |
| `App:TimeZone` | API, Worker | IANA zone for dates in email; default `Europe/Istanbul`. |
| `Email:Mode` | Worker | `Smtp` or `Pickup`. No default in `appsettings.json`; Development sets `Pickup`. |
| `Email:From` | Worker | Sender address, e.g. `ProteoSM <no-reply@proteosm.local>`. Not used while the panel mail settings are active (ADR-0045). |
| `Email:Smtp:Host`, `Port` (587), `UseStartTls` (true), `UserName` | Worker | SMTP transport settings. While the panel mail settings are active, `Smtp` mode sends with them instead; `Email:Mode` and `TimeoutSeconds` always come from the environment (ADR-0045). |
| `Email:Smtp:TimeoutSeconds` | Worker | Deadline for one whole SMTP send (default 30). The `EmailSender` lease (`Worker:Jobs:EmailSender:LeaseSeconds`) must be greater, else startup fails. |
| `Email:Smtp:Password` | Worker | Secret: user-secrets or environment only; never in `appsettings`, logs, audit or `last_error`. |
| `Email:PickupFolder` | Worker | Folder for `.eml` files in `Pickup` mode. `tools/run.sh` and `tools/e2e.sh` pass an absolute `tmp/email-pickup` path. |
| `Files:RootPath` | API, Worker | Folder for attachments and export files. Both hosts must point at the same absolute folder (the Worker writes export files the API serves); required outside Development, where startup fails without it. Empty in Development means the user's local application data folder (`proteosm/files`). Both hosts log the resolved root at startup (`File store root: …`). `tools/e2e.sh` sets a per-run temp folder. |
| `DataProtection:KeysPath` | API, Worker | Key ring folder, shared by both hosts (ADR-0024). Required outside Development; empty in Development keeps the framework's per-user default. Docker images set `/data/keys`. |
| `Http:KnownProxyNetworks` | API | CIDR list of reverse proxies whose `X-Forwarded-For` / `X-Forwarded-Proto` are applied outside Development (ADR-0024). Compose passes `PROTEOSM_SUBNET`. Development trusts only the loopback Vite proxy. |
| `Worker:Jobs:<Job>:IntervalSeconds`, `BatchSize`, `LeaseSeconds` | Worker | Per job. `OutboxDispatcher` and `EmailSender`: 30 s / 50 / 60 s. `SlaMonitor`: 60 s, batch 200. `Cleanup`: hourly (3600 s). `ExportRunner`: 30 s / 5 / 600 s (Development 5 s). A non-positive interval falls back to the job default and logs a warning. |
| `Worker:Jobs:<Job>:IntervalSeconds` | API | The API reads the same section (duplicated in its `appsettings.json`, default 60 s) to judge a job stale for `/health` and `/admin/system/workers`. |
| `Security:LoginPermitLimitPerMinute`, `ForgotPasswordPermitLimitPerMinute`, `SetPasswordPermitLimitPerMinute` | API | Per-client-IP limits per minute; defaults 10, 5, 5. `tools/e2e.sh` raises the login limit and shortens the two job intervals, and sets `App:PublicBaseUrl`, `Email:Mode=Pickup`, `Email:PickupFolder` for the run (E2E only). |

Deployment settings (`deploy/.env`, template `deploy/.env.example`, read by `tools/compose.sh`): `PROTEOSM_DEPLOYMENT` (unset on production; `pilot` only on a pilot or test host, required by `tools/seed-pilot.sh --compose`), `POSTGRES_PASSWORD`, `PUBLIC_BASE_URL` (→ `App:PublicBaseUrl`), `HTTP_PORT`/`HTTPS_PORT`, `TZ`, `APP_TIME_ZONE` (→ `App:TimeZone`), `PROTEOSM_SUBNET` (→ `Http:KnownProxyNetworks`), `EMAIL_MODE`, `EMAIL_FROM`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USE_STARTTLS`, `SMTP_USERNAME`, `SMTP_PASSWORD` (→ `Email:*`), `BACKUP_TIME`, `BACKUP_RETENTION_DAYS`, `BACKUP_HOST_DIR`. The image tag `PROTEOSM_VERSION` is not set in `deploy/.env`: `tools/deploy.sh` records the deployed Git short hash in `deploy/.version` (git-ignored) and `tools/compose.sh` exports it; a `PROTEOSM_VERSION` in the shell environment overrides the file. The images set `Files:RootPath=/data/files` and `DataProtection:KeysPath=/data/keys`; compose sets `Email:PickupFolder=/data/files/email-pickup`. Meaning of each: `docs/operations.md`.

## API

All routes are under `/api/v1`. Errors are RFC 7807 ProblemDetails with a stable `code` and an optional `errors` map (field → codes). Unknown `/api/*` routes return 404 `common.not_found`. Every unsafe request needs the `X-CSRF-TOKEN` header, multipart uploads included.

### Auth

| Method | Path | Behavior |
|---|---|---|
| GET | `/auth/csrf` | Anonymous. Returns `{ token }` and sets the antiforgery cookie. |
| POST | `/auth/login` | Anonymous, rate limited per IP (`Security:LoginPermitLimitPerMinute`, default 10). `{ email, password }` → `{ mustChangePassword }` and session cookie. Every failure: 401 `auth.invalid_credentials`. |
| POST | `/auth/logout` | Ends the session (204). |
| GET | `/auth/me` | Current user (`MeDto`). Allowed while a password change is pending. |
| POST | `/auth/forgot-password` | Anonymous, rate limited per IP. `{ email }` → always 202, same work for every address; the Worker resolves the account later. A reset link is sent only for an active account without an unused reset link younger than 15 minutes. |
| POST | `/auth/set-password` | Anonymous, rate limited per IP, one call per link. `{ token, newPassword }` → 204. Every invalid, used or expired token: 400 `auth.token_invalid`. Sets the password, clears the forced change, ends other sessions and voids the user's other unused links. |
| POST | `/auth/change-password` | `{ currentPassword, newPassword }` → 204; re-issues the cookie; other sessions end. |
| GET | `/auth/method` | Anonymous. `{ method }` (`local`, `entra`, `ldap`); the login page follows it. |
| GET | `/auth/oidc/start` | Anonymous, rate limited. Full-page redirect to Microsoft; 404 unless Entra is the method. The callback `/auth/oidc/callback` signs the user in, or sends a refusal to `/login?error=sso`. |
| POST | `/auth/login/ldap` | Anonymous, rate limited. `{ identifier, password }` (Windows user name or email) → `{ mustChangePassword }` and session cookie; 401 on any failure, 503 when the directory cannot be reached. |

### Search (signed in, ADR-0033)

| Method | Path | Behavior |
|---|---|---|
| GET | `/search` | `q` (2–100 characters, `SearchLimits`, else 400 `search.query_invalid`). Returns `{ exact, groups }`: `exact` is the hit for a full record number (or, for staff, an asset tag of at least 4 characters without spaces) the viewer may open, else null and the search falls through silently. `groups` per type (`ticket`, `change`, `task`, `problem`, `asset`, `service`, `article`), at most 5 hits each (`key`, `title`, `status`) and `hasMore`. Scopes: tickets `TicketScope.Visible`, changes `ChangeScope.Visible` (summary access included), tasks `TaskScope`, problems `ProblemScope` (every problem for IT staff and admins; a full `PRB-` number is an exact hit), articles `ArticleAccess`; assets for IT staff and admins only, by tag or serial (brand and model are not searched), newest update first; services for IT staff and admins only, by name or description, active first, key = service id, status `Active` or `Inactive` (ADR-0036). Employees get tickets and articles only |

Window conflicts (a warning only, never a block): two changes conflict when their windows overlap (half-open `[start, end)`, so back-to-back windows do not) and they share an affected asset or the same non-empty `affectedService` (Turkish-aware, case-insensitive comparison). Working-summary viewers get no `conflicts`. `conflictCount` on `/change-approvals` counts the same clashes for each pending change.

## Auth & permissions

- Session cookie `__Host-proteosm` (Secure, HttpOnly, SameSite=Strict, 8-hour sliding, at most 24 hours after sign-in). Every request re-reads the user: inactive users and changed security stamps end the session. Role change, (de)activation, password change and admin reset rotate the stamp.
- Antiforgery token required in `X-CSRF-TOKEN` on every unsafe `/api` request, including login and uploads.
- Lockout: 5 failed logins → 15 minutes; the counter is updated atomically. Inactive and locked accounts cost the same hash check as others.
- Password: 12–128 characters with a letter and a digit. Temporary passwords: 16 random characters, shown once.
- Fallback and default authorization policies require a signed-in user whose password change is not pending; `/admin/*` and `/approvals/*` need `admin`; `/assets/*` (except `/me/assets`), `/reference/users` and `/reference/teams` need IT staff or admin.
- Ticket scope (ADR-0013): employees see their own tickets and public content only; IT staff see their own tickets and their teams' tickets with internal content; admins see all. Work actions need admin or membership in the ticket's team. Out-of-scope numbers and ids return 404 everywhere, including attachments.
- `/admin/email-templates`, `/admin/email-deliveries`, `/admin/sla/*` and `/admin/system/*` sit under the `admin` policy like the rest of `/admin/*`. `GET /health` and the account-link endpoints (`/auth/forgot-password`, `/auth/set-password`) are anonymous.
- Knowledge base (ADR-0019): any signed-in user may call the read endpoints, but employees see only `published` + `employees` articles; any other article is 404 on list, detail and search, and its ticket links are not shown to them. Create, edit, status actions and revisions need IT staff or admin. Linking and unlinking articles on a ticket need IT staff or admin and a ticket in their scope.
- Reports (ADR-0020): `/reports/*` need IT staff or admin (employees 403), except `/reports/exports/{id}/download`, which needs a signed-in user and checks in the handler that the caller created the job and is still active IT staff or admin (otherwise 404). Admins see all tickets; IT staff see only tickets whose current `team_id` is one of their teams, not tickets they merely requested. Asset and warranty reports show all assets to both roles. A background export is built under the creator's scope at run time; a creator who is inactive or no longer IT staff or admin by then fails the job (`last_error` `common.forbidden`) without a file.
- Password set links (ADR-0017): activation links last 72 hours, reset links 1 hour, each works once. A user's unused links are revoked when the user sets a password, when an admin changes the email address, and when an admin issues a temporary password. An account email queued before an email change is never sent to the new address. A forgot-password request is skipped (no link, no email) while the account has an unused reset link younger than 15 minutes; this also counts a link an admin issued. Every forgot-password request answers 202 and does the same work on the request path for any address, so the response does not reveal whether an account exists.
- Login method (ADR-0030): one active method. Under Entra only members of the configured tenant with an allowed email domain sign in (guests refused; the sign-in name is the email, never the `email` claim). Under LDAP the service account finds the entry and a bind as that entry checks the password; attempts are counted per typed name and per found account (5, then the lockout window). A directory identity links by stored id, else by the same email, else creates an employee without a password; roles stay in Proteone. Under a directory method only admins can still use a local password (break-glass). A method goes live only after its connection test passed with the current settings; switching back to local sends a set-password link to every active user without a password.
- Tasks (ADR-0031): employees never see tasks (404 on every task route, empty task queues). A task is visible to admins, members of its team, its assignee and its creator; work actions need admin or membership in the task's team. A task stays visible to an assignee who left the team, but that person cannot work on it.
- Changes (ADR-0031, ADR-0032): employees get 404 on every change route. Full detail: admins, members of the owner team, and admins who decided or may decide the pending approval. Working summary: members of a team with a task on the change and those tasks' assignees see number, title, status, window, risk and the plan for their phase (implementation plan for Hazırlık/Uygulama/Doğrulama tasks, backout plan for Geri dönüş tasks); never approvals, history, conflicts or other teams' tasks. Owner team members and admins edit and run the change and add change tasks. An approval is decided by an active admin who is not the author, not the owner and not in `change_plan_editors`; one shared query decides this for the decision, `canDecide`, the approvals list, `hasEligibleApprover` and the approval-request email recipients.
- Ticket-change links (ADR-0033): a link shows the number, title, status and team of the other record to IT staff who may see either side, also when they cannot open it (`canOpen` false); opening still follows that record's own scope. This is the one disclosure exception to ADR-0013. Employees never see links (404 on `/tickets/{number}/changes`). Adding and removing links needs admin or owner-team membership of the change.
- Central search (ADR-0033): one endpoint applies the existing scope classes per type, so it shows nothing the lists do not. A full number outside the viewer's scope gives no exact hit and no error.
- Problems (ADR-0034): employees get 404 on every problem route and see no problem data on tickets. Every active IT staff member and admin reads every problem. Create: any IT staff member or admin, for one of their own teams (admins: any team). Writes on the problem (edit, state actions, transfer, owner, notes, "Makale oluştur", change links) need an admin or a member of the owner team; others get 403 `common.forbidden`, because they can see the record. An incident link may also be added or removed by anyone who may work on the incident (admin or member of its team), so the desk can attach a repeat incident to another team's problem. Linked incidents and changes outside the viewer's scope show number, title and status without a link (`canOpen` false).
- Services (ADR-0036): admins create, edit, activate and deactivate services and link and unlink assets (`/admin/*` policy). Active IT staff and admins read the list, detail, impact view and an asset's services, and may set the service on any ticket they can see; on changes and problems the set-service action follows the record's write rule (admin or owner team). Employees get 404 on every service route (the handlers answer not found, so employees cannot tell services exist), 403 on `GET /tickets?serviceId=`, and no service field in their ticket DTOs. Impact rows outside the viewer's ticket or change scope show number, title and status without a link.
- Development only: the API trusts `X-Forwarded-Proto` from the loopback Vite proxy so Secure cookies work on `http://localhost`.

## Features & business logic

- **First admin / recovery:** `tools/setup-admin.sh` works once and refuses when any user exists (ADR-0007). `tools/reset-password.sh --email …` issues a temporary password from the console; the user must change it at next sign-in. On a deployed stack the same commands run as `tools/compose.sh run --rm api setup-admin …` / `reset-password …` (`docs/operations.md`).
- **Users:** email unique ignoring case; department/location must be active when newly assigned; the last active admin cannot be demoted or deactivated (serialized with an advisory lock); a user's own sign-ins and password change do not make an admin's open edit stale.
- **Search and names:** Turkish-aware keys (`tr-TR` lower case, dotless ı folded to i), so "IT Destek" and "it destek" are the same name and "yazici" finds "Yazıcı".
- **Locations:** a location cannot move under itself or a descendant; a parent with active children cannot be deactivated; a child of an inactive parent cannot be reactivated.
- **Teams:** only active IT staff and admins can be members; inactive teams accept no new members; exactly one team can be the default intake team (moving the flag is serialized).
- **Asset lifecycle (ADR-0010):** `in_stock` → assign → `assigned`; return, transfer, maintenance (optionally keeping the user responsible), lost/found, retire. Operations are serialized; concurrent handovers give one active assignment and 409 for the rest. Every operation writes a movement and an audit row.
- **Handover against a request:** only to the open request's requester, and only after a required approval is granted (`assets.request_mismatch`, `tickets.approval_required`).
- **Device catalog and tags (ADR-0023):** brand and model names are unique by `CatalogName.Normalize` (whitespace collapsed, Turkish-aware key). Renames rewrite the asset snapshots in the same transaction; asset create, edit and import commit take the same `SerializationLocks.AssetCatalog` lock, so no asset keeps a name read before a rename. Tags are `ASSET-` + company calendar year + a yearly number of at least four digits from `asset_tag_counters` (ADR-0029); they are never reused (a rolled-back save leaves a gap), skip numbers an existing tag already holds, and are never typed by a person or read from a file. The post-migration step `RenumberAssetTagsStep` turned every older tag (`DMR-` and hand-typed legacy tags) into the new format once, per year in creation order, audited as `assets.tag_renumbered`.
- **Incident device (ADR-0028):** `POST /tickets/incidents` takes an optional `assetId`; any existing device whose status is `in_stock`, `assigned` or `maintenance` may be named (others and unknown ids: `tickets.asset_not_reportable`). The form lists only the requester's own devices; other devices arrive through a scanned QR label. The device is linked to the new ticket; the link is recorded as an `AssetLinked` timeline event after `Created` and a `TicketAssetLinked` audit entry, like a later link.
- **Work actions and replies:** ticket work buttons are disabled while a reply is being sent or the ticket is refetching, because a reply changes the ticket version and a dialog keeps the version it opened with.
- **CSV import:** strict UTF-8 (`imports.encoding` explains how to save from Excel), `,` or `;`, dates `yyyy-MM-dd` or `dd.MM.yyyy`; location by full or unique trailing path; brand, type and model must exist in the active catalog (`assets.import_catalog_missing`, "Tanım eksik"); every row gets a generated tag at commit (the template has no tag column; an old file's "Demirbaş No" column is not read); duplicates inside the file and against the database reported per row; `assigned`/`lost` refused; one bad row blocks the whole commit; commit re-checks conflicts and is idempotent.
- **Ticket closing time:** `tickets.completed_at` is set when a ticket is completed, cancelled, or cancelled by approval rejection (`approval_rejected`). It is the "closed at" instant that reports use as the completion date basis. No migration backfills rows closed earlier.
- **Knowledge base search (ADR-0019, ADR-0006):** the key is the trimmed text lower-cased with `tr-TR` rules (`I`→`ı`, `İ`→`i`), then `ı` folded to `i`, so "Yazıcı" and "yazici" match (stored text is folded the same way) and "Isik", "ısık" and "İsik" match each other. Other diacritics (`ş`, `ç`, `ğ`, `ö`, `ü`) are not folded: "sifre" does not find "şifre", "gorev" does not find "görev". Input with no letter or digit means no search. Matching is substring over `search_text` through `LIKE '%key%'` (`LikePattern.Containing`, with `%`, `_` and `\` escaped so they match literally), which the trigram GIN index serves; ticket search uses the same pattern. An article summary may be empty. Markdown headings render one level down (`#` → `<h2>`, capped at `<h6>`) so the article title stays the page's only `<h1>`. A session whose user no longer exists gets 401 on knowledge base calls, not a server error.
- **Article revisions:** only create and edit (content changes) bump `revision` and write an `article_revisions` row; publish, archive and restore keep it. Visibility changes, publish, archive and restore are audited (`knowledge.visibility_changed`, `knowledge.published`, `knowledge.archived`, `knowledge.restored`; also `knowledge.created`, `knowledge.updated`, `tickets.article_linked`, `tickets.article_unlinked`).
- **Public-reply guard:** a public ticket comment whose body contains a `/kb/{uuid}` link to an `internal` article is refused with `knowledge.internal_article_in_public_reply`; the check is on the server, the reply picker is a convenience.
- **Report consistency:** a figure, its drill-down rows and its export are produced from the same filtered query and metric predicate, so counts agree. Exports write one data sheet plus a `Filtreler` sheet with the filters and scope; Turkish headers come from `ExportHeaders.tr.json`. Cell values are stored as text or numbers, never as formulas.
- **Background export (ADR-0020, ADR-0014):** a job is created `pending` (per-user cap of 3 pending or running jobs checked under `SerializationLocks.ExportQueue`). `ExportRunner` claims due jobs (`pending`, or `running` with an expired lease) with a row lease, renews each job's lease before working on it and skips a job another run took over. Each start counts an attempt; a job that has already started 3 runs (`ReportExportLimits.MaxAttempts`) is failed with `reports.export_attempts_exhausted` instead of running again, so a job that crashes the Worker cannot loop forever. The runner reads the same rows as the drill-down under the creator's current scope, fails the job with `reports.export_too_large` when it has grown past 100,000 rows, writes the file through `IReportFileWriter` into `IFileStore` and marks it `ready` with `row_count` and `expires_at` = now + 24 h. A failed write leaves no file; a failure is recorded from a fresh scope, only while this run still holds the lease, with a sanitized `last_error`.
- **Dev services:** `tools/dev-service.sh install` registers three launchd user agents (`com.proteosm.dev.api`, `.worker`, `.web`) that start at login and restart on exit (10 s throttle); logs in `tmp/logs/`. API and Worker start through `tools/dev-dotnet-host.sh`, which builds into `tmp/dev-artifacts/<name>/build`, copies a good build to `current/`, and falls back to the last good build when the build fails.
- **Ticket lifecycle:** open → in_progress → completed; open/in_progress ↔ on_hold (reason, "other" needs a note); cancel with a reason; no reopen. Completion needs a user-visible resolution; incidents need an outcome, `service_request_required` needs a related request; requests needing approval need a granted approval. Completed tickets still accept comments.
- **Priority:** impact × urgency matrix (P1–P4), default medium/medium = P3; IT changes it with a reason, old and new values audited.
- **Assignment:** IT claims unassigned tickets of their team (concurrent claims: one wins); transfer needs a reason ("other" needs a note) and an assignee who is an active member of the target team.
- **Tasks (ADR-0031):** `TSK-YYYY-NNNNNN` numbers. States `open` → `in_progress` ⇄ `on_hold` (reason) → `completed` (result note required) or `cancelled` (reason); reopen from `completed`/`cancelled` to `open`. Claim is one conditional update (no assignee, same team, same version, still open): of parallel claims one wins, the rest get 409. Transfer moves the task to another team, clears the assignee and returns running work to `open`; clearing the assignee of running work also returns it to `open`. Overdue = due date before today in the company time zone while open; tasks have no SLA. The ticket link is fixed at creation; task actions never change the linked ticket, its version or its SLA timers. Notes touch only `updated_at` and change the row version, so the detail refetches before the next action. `task_assigned` email goes to the new assignee, or to the team's active members when a transfer leaves it unassigned. Audited: `tasks.created`, `tasks.assigned`, `tasks.transferred`, `tasks.status_changed`.
- **Change calendar and conflicts (ADR-0032):** a conflict is a warning, never a block; submit, approve and schedule work as before. Overlap is half-open, candidates are `pending_approval`, `scheduled` and `implementing` changes whatever the viewer may see (a hidden clash is reported without number and title), and an asset match wins over a service match as the reason. The calendar range is capped at 62 company days (`changes.calendar_range` is a 400, not a 409, because it is a bad query) and it shows `hasConflict` only where the viewer has full access, so a summary viewer learns nothing about changes of other teams. `this_week` is by window start, not by overlap with the week.
- **Changes (ADR-0031, ADR-0032):** `CHG-YYYY-NNNNNN` numbers. States `draft` → `pending_approval` → `scheduled` → `implementing` → `verifying` → `closed` (outcome `successful`, `rolled_back`, `failed`), or `cancelled` (reason) from `draft`, `pending_approval`, `scheduled`. Approval is single-stage and unassigned: any eligible admin decides; approve moves to `scheduled`, reject and return send the change back to `draft` with a reason, the author withdraws. A decision is one conditional update on `status = pending` and the approval version, so of parallel decisions one wins. The approval stores a SHA-256 fingerprint over window, sorted asset ids, risk, impact, the three plans and the sorted ids of open-or-completed Uygulama tasks; an edit of these in `scheduled` voids the approval (reason code `changes.reason.plan_changed`), returns to `pending_approval` and mails the admin who approved; title, justification and closing note do not void it. Everyone who submits or changes the plan (fingerprint fields, assets, Uygulama tasks added, cancelled or reopened, in any status including `draft`) is recorded in `change_plan_editors` for the life of the change and never decides it. Task gating: Hazırlık tasks run in `scheduled`, `implementing` and `verifying`, Uygulama tasks only in `implementing`, Doğrulama tasks only in `verifying`, Geri dönüş tasks only after backout started; a change task reopens only while the change is open. Closing Başarılı needs `verifying`, a verification note, actual start and end (end not before start, `changes.end_before_start`), no open Uygulama task and at least one completed one (cancelled ones are ignored, because a cancelled Uygulama task cannot rejoin a locked plan), every Doğrulama task completed, every Hazırlık task completed or cancelled; open Geri dönüş tasks are cancelled with reason code `changes.reason.not_needed`. Geri alındı / Başarısız need backout started, at least one Geri dönüş task, all of them closed, and a backout note. Every change state change and change-task write runs under `SerializationLocks.ChangeWork`, so a close never races a task completion. Backend-written reasons are stored as codes and translated in the frontend (ADR-0006). Emails: `change_approval_requested` (eligible admins; skipped when the change no longer waits for approval at dispatch), `change_approval_decided` (author and owner; shows the decided row's outcome and reason), `change_backout_started` (Geri dönüş assignees, or their teams' active members when unassigned).
- **Ticket-change links (ADR-0033):** a link has a kind: `prompted` (the ticket led to the change) or `caused` (the change led to the ticket; incidents only). One link per pair. Links can be added to a change in any status except `cancelled`; removal stays allowed there so a wrong link can be cleaned up. A link touches the ticket's `updated_at` like a comment, which also moves its row version, so a ticket dialog opened before the link gets 409 and reloads. Both sides get an audit row and a timeline event; the ticket's event is internal.
- **Central search (ADR-0033):** text is trimmed and must be 2–100 characters. A full visible record number (or an asset tag of at least 4 characters without spaces, for staff) is the exact hit; otherwise each type returns up to five substring matches (`LikePattern.Containing`, trigram indexes) and a `hasMore` flag. A number outside the viewer's scope is not reported. Assets match only by tag or serial, because brand and model searches would bypass the trigram indexes and Turkish casing rules.
- **Problems (ADR-0034):** `PRB-YYYY-NNNNNN` numbers. States `open` → `investigating` (İncelemeye al); `open`/`investigating` → `known_error` once root cause and workaround are both filled; `open`/`investigating`/`known_error` → `resolved` (permanent fix note required) or `cancelled` (reason required, e.g. a duplicate). No reopen: a recurrence opens a new problem. Title, symptom, impact, root cause and workaround stay editable until resolved or cancelled. An incident belongs to at most one problem (unique index); requests cannot be linked; a resolved or cancelled problem takes no new links. A link touches the ticket's `updated_at` (internal timeline event `problem_linked` / `problem_unlinked` on the ticket, and on the change for change links) and never its status, SLA or version rules. All link writes and the state changes that close a problem run under one global `SerializationLocks.ProblemLink` key, so "one incident, two problems" and "link onto a problem being closed" end in 201 or 409, never 500. "Makale oluştur" (in `known_error` or `resolved`, once) creates an `internal` `draft` article "Bilinen hata: <title>" with the headings Belirti, Kök neden, Geçici çözüm (and Kalıcı çözüm when resolved) and the problem number, in one transaction with the problem update, so a double click makes one article and a 409; later problem edits do not rewrite it, and publishing follows ADR-0019. Transfer moves the problem to another team with a reason and clears the owner. The workspace card counts only open problems of the viewer's teams (`team_open`). SLA and email: see the next bullet (ADR-0046).
- **Problem SLA and email (ADR-0046):** a separate timer beside the ticket SLA, which stays unchanged. `CreateProblemHandler` starts one timer per new problem from the current target of its impact, on the company calendar; problems created before the deploy have none (no backfill, so no burst of breach mail). The timer stops at known error or at a resolve from open/investigating (`met` when at or before `due_at`, else `breached`); a resolve after known error keeps the stored result; a cancel sets `cancelled`. An impact change re-targets a running timer and a calendar or holiday change re-plans it, exactly like `SlaInstance.ChangeTarget` / `ApplyCalendarChange` (breach stays recorded, warning mark resets below the new threshold). `MonitorSlaHandler` runs a second pass over problem timers with conditional updates, so two Workers write one warning and one breach. The timer has no concurrency token, so the monitor and a user's stop or re-target never fail each other with 409. Mails (outbox, recipients at dispatch, inactive users skipped): `problem_created` to the owner-team members except the actor and an owner given at creation; `problem_assigned` to a new owner, or to the new team on transfer; `problem_sla_warning` / `problem_sla_breached` to the owner, else the team; `problem_known_error` / `problem_resolved` to the assignee (else team) of each linked incident that is not completed or cancelled, once per person, actor excluded; `ticket_cause_found` / `ticket_cause_resolved` to the requester of each such incident, with ticket variables only (`TicketCommon`) — the template validation refuses problem variables there, so no problem number, title, cause or workaround reaches an employee. Problem templates add `problemNumber`, `problemUrl`, `impact`. The pilot seed closes the problem mails it queues.
- **Services (ADR-0036):** a service has a unique name (Turkish-aware normalized key), an optional description, a required owner team (checked to be active on create and when the owner changes, so a service whose team was deactivated later stays editable) and an active flag; create and edit run under `SerializationLocks.ServiceCatalog`; there is no delete, no status, health, SLA or service hours. Only an active service can be set on a record (`services.inactive`); clearing is always allowed and an inactive service already on a record stays. The set-service action skips the lifecycle guards, so closed tickets, changes and problems can be tagged for history; it never changes status, SLA, `completed_at` or version rules beyond the record's own concurrency check, is not part of `ChangePlanFingerprint` and never voids a change approval. The free-text change field `affectedService` stays and still drives the window-conflict "Aynı hizmet" reason. A `retired` or `lost` asset cannot be linked (`services.asset_not_linkable`); an existing link stays when the asset is later retired or lost, and the impact view shows its status. Link and unlink run under `SerializationLocks.AssetLifecycle`, so the status check cannot race an asset retire or "lost" mark; the unique pair index is the second guard (`services.asset_link_exists`). The service suggestion is a hint only: the service never routes a ticket, picks a team or changes an SLA.
- **Licences (ADR-0039):** seats, quantity changes and the hourly expiry job run under lock 7_013; a deactivated user or retired asset keeps the seat and is marked; one `licence_expiring` email per licence and end date, the notice days of the general settings (30 at first) before the end.
- **Releases (ADR-0040):** writes run under the change lock; joining never changes the plan, approval or state of a change; completion needs at least one change and all of them closed or cancelled.
- **Monitoring (ADR-0041):** one lock per source, replay by event id, at most one firing note in 5 minutes (always after a "resolved" note), 30 incidents an hour per source, incidents are closed by hand.
- **Directory contract test (ADR-0030):** `tools/directory-contract-test.sh` runs `OidcContractTests` on the host against `mock-oauth2-server`, then `NovellLdapDirectoryTests` and `LdapApiContractTests` over LDAPS (636) and StartTLS (389) inside a .NET SDK container that trusts a throw-away CA, then `LdapOutageContractTests` with OpenLDAP stopped (503 `auth.directory_unavailable`). `--fail-skips on`: a skipped test fails the run. It starts Colima when needed and stops it again only if it started it; containers and volumes are removed on every exit path. Fake data only; results and open gaps (mock fidelity, OpenLDAP instead of Active Directory) are in `docs/release/directory-contract-test.md`. A real Entra tenant and a real Active Directory are still needed before go-live.
- **Approvals:** approver is the requester's department approver when that is an active admin other than the requester, otherwise unassigned until an admin reassigns it. Only the assigned approver decides; approve opens the request, reject cancels it with outcome `approval_rejected`; concurrent decisions: one wins. Cancelling a ticket voids its pending approval.
- **Numbers:** `INC-YYYY-NNNNNN` / `REQ-YYYY-NNNNNN` from a counter row locked in the creating transaction, so concurrent creation never repeats a number.
- **Comments and files:** employees write public replies on their own tickets; internal notes need someone working on the ticket. Files inherit the comment's visibility; extension must match content; a failed save deletes stored files. Comments and links do not conflict with a status change made at the same moment.
- **Concurrency:** stale edits return 409 `concurrency.conflict`; the UI shows a Turkish message; dialogs send the version the user saw when opening them.
- **Worker:** `ProteoSM.Worker` runs five jobs: `OutboxDispatcher`, `EmailSender`, `SlaMonitor` (every 60 s), `ExportRunner` (every 30 s) and `Cleanup` (hourly) (ADR-0014). Each iteration runs in its own DI scope, a failure is logged and recorded and never stops the loop, and every run upserts a `worker_heartbeats` row (error text in `last_error`). Claims use `RowLease` (`FOR UPDATE SKIP LOCKED`); a crashed instance's rows become claimable again after `locked_until`. Email deliveries and outbox events are also re-claimed one row at a time by a conditional update on the lease value before processing, and completion writes are guarded by that ownership, so a run whose lease expired mid-batch cannot send or dispatch a row again or move a `sent` row back to `pending` (ADR-0014). The Worker has no signed-in user: audit rows it writes carry no user id and a generated correlation id.
- **Notification events:** ticket, approval and SLA code add an event through `INotificationOutbox` before the single save, so the event commits with the change and a rollback leaves none. Events and recipients (resolved at dispatch time from current data, inactive users never receive email): `ticket_created` (requester), `ticket_assigned` (new assignee, or team members when unassigned; not the actor), `public_reply` (requester, or assignee/team when the requester wrote it; not the author), `approval_requested` (approver), `approval_decided` (requester), `ticket_completed` (requester), `sla_warning` and `sla_breached` (assignee, or the team's active members when unassigned), `account_activation` and `password_reset` (the account). `password_reset_requested` is internal (the normalized address in its payload, resolved by the dispatcher; no delivery of its own). Every event carries the acting user's id in its payload; payloads hold ids and reason codes only.
- **Dispatch:** `OutboxDispatcher` claims pending events, resolves recipients, renders subject and body from the event's template and inserts `email_deliveries` rows, one event per DI scope. No recipient marks the event `skipped`. A failing event records an attempt on itself only (same back-off and limit as deliveries), so one bad event cannot block the rest; after 5 failed attempts it becomes `failed`. The failure is recorded from a fresh DI scope so the failed save is not retried. Rendered subject and body are cut to the column limits (200 and 10,000 characters, never inside a surrogate pair) so a long ticket subject cannot make the insert fail.
- **Sending:** `EmailSender` claims due deliveries in id order (`sending`, leased), sends through `IEmailSender`, marks `sent`. A failure adds an attempt and schedules the next one after 1, 5, 15 and 60 minutes; the 5th failed attempt sets `failed`. A failure is recorded in a fresh scope, only while the row is still `sending` under this run's lease. Each send is bounded by `Email:Smtp:TimeoutSeconds`. A delivery left `sending` by a crashed worker is reclaimed once its lease expires. Delivery is at-least-once: a crash after the transport accepted the message but before `sent` was saved can repeat one email (ADR-0015).
- **Transports:** `Smtp` uses MailKit (STARTTLS when `UseStartTls`, credentials only when configured); `Pickup` writes `.eml` files, so local runs and tests need no mail server. Send errors are sanitized (type name and message, `password`/`secret`/`token`/`authorization` pairs redacted, cut to 500 characters) before they reach `last_error`.
- **Outgoing mail settings (ADR-0045):** `Email:Mode` stays the source of truth. In `Smtp` mode the Worker sends with the panel settings while the row is active, else with `Email:From` + `Email:Smtp:*` as before; `Pickup` ignores both. `ActiveSmtpEndpointProvider` caches the row for 10 s, then reloads only when `xmin` changed, so a change applies without a restart. Use needs a passed test whose fingerprint (SHA-256 over every field incl. the protected password) matches the current settings. A save of active settings runs the test first and is refused when it fails, so a wrong save never stops mail; a failed test on active settings changes nothing and never falls back to `.env` silently. The password is write-only and never sent to a new server or login without being typed again. `SmtpTargetPolicy` checks the panel host after DNS resolution (test send and Worker): link-local, unspecified, cloud metadata and translation-prefix addresses are refused, IPv4-mapped forms are unwrapped; private and loopback stay allowed for internal relays. Errors in test results and `last_error` are sanitized and the password is replaced by `[redacted]`, also in its base64 `AUTH PLAIN` / `AUTH LOGIN` forms.
- **Satisfaction rating (ADR-0044):** only the requester rates, once per ticket, changeable inside the window (latest value counts). Rateable: `completed` with outcome `resolved` or `fulfilled`; the window ends 14 days after `completed_at` (`RatingLimits.Window`). The rating touches `updated_at` like a comment (no version check), adds the internal timeline event "Puan verildi", and two first ratings at once leave one row (the other request gets 409). The `ticket_completed` template has the variable `ratingUrl` (`App:PublicBaseUrl` + `/tickets/{number}?rate=1`), filled only for a rateable ticket; a line whose only variables are empty optional ones is dropped, so a mail without a link has no empty line. The comment is never emailed. The pilot seed rates some completed tickets.
- **Email templates:** plain text only (problem events and their variables: ADR-0046). Variables are `{{name}}` substitutions from a fixed per-event list: ticket events `ticketNumber`, `subject`, `status`, `ticketUrl`, `recipientName`; `ticket_completed` adds `resolution`, `completedAt`; SLA events add `slaMetric`, `dueAt`; account events allow only `recipientName`, `actionUrl`, `expiresAt`. An unset variable renders as empty text. Dates use the company time zone (`App:TimeZone`) as `dd.MM.yyyy HH:mm`. Subject (max 200 characters) and body (max 10,000) are required; variables are checked in both.
- **Account-link emails:** the link token is stored only as `protected_secret` (ASP.NET Core Data Protection, purpose `Tgysm.Notifications.AccountLinkToken`). The body renders at send time; after `sent` or a terminal `failed` the secret is cleared and the delivery body becomes `[cleared]`. A retryable failure keeps the secret so the next attempt can render the link. Link: `App:PublicBaseUrl` + `/set-password?token=…`. Admin retry of a failed account email issues a new token onto the same event and revokes older unused ones; the old secret is not reused.
- **Business time (ADR-0018):** `BusinessTimeCalculator.SecondsBetween` and `AddSeconds` work over `BusinessCalendarRules` (zone, one optional working range per weekday, holidays). Each UTC boundary is converted to local time per day and clipped to the working range; holidays and closed days count zero; DST gaps lose the skipped hour. Results are UTC. `sla.calendar_empty` is the error for a calendar with no working time.
- **SLA instances (ADR-0018):** creating a ticket starts a `first_response` and a `resolution` instance on the current policy version (a request-type target overrides the priority target; a request starting `on_hold` for approval starts with resolution paused). A running instance keeps the targets and pause rules of the version it started on. A hold pauses the timers its reason's rule names; resume and approval grant restart them. A priority change gives each instance the new priority's target of its own version and resets the warning while still below the threshold. First response stops at the first public reply by IT staff or an admin other than the requester; both stop on completion (result `met` or `breached`) and cancellation (`cancelled`). Transfers never reset a timer.
- **Calendar change re-plans running timers (ADR-0018):** changing the calendar or adding or removing a holiday recomputes `due_at` and `warn_at` of running (not paused, not stopped) instances: elapsed business time under the old rules is kept, the remainder runs under the new rules, and a `calendar_changed` event is logged. The re-planner locks the instances it changes. Known limit: a ticket action that read the old calendar just before the change and saves just after it computes its own due time under the old rules until the next pause, resume or priority change.
- **SLA monitor:** `SlaMonitor` marks running instances past `warn_at` or `due_at`. Each mark is a conditional update (`warned_at` / `breached_at` still empty, not stopped), one transaction per instance, so of several monitors one wins and only it writes the `sla_events` row and the `sla_warning` / `sla_breached` outbox event. A breach of an instance never warned also warns first. It writes only those columns, so it never fails a user's ticket action. Paused instances do not warn or breach.
- **Worker status and health:** each job's newest heartbeat is judged stale after 3 × its interval; `GET /admin/system/workers` lists jobs, `GET /health` returns only `ok` or `degraded`.
- **Cleanup:** hourly, with a 30-day retention cutoff. Deletes password tokens that expired before the cutoff; `dispatched` or `skipped` outbox events older than the cutoff whose deliveries are all `sent` or `failed` (deliveries go with the event); `password_reset_requested` events (they hold an email address) that are no longer `pending` and are older than the cutoff; and `worker_heartbeats` rows not updated since the cutoff. It also expires `ready` export jobs past `expires_at`, in batches of 100 (`CleanupHandler.ExportExpiryBatchSize`): the file is deleted first, then the job is marked `expired` (xmin-guarded); a file that cannot be deleted is logged and its job stays `ready` for a later run.
- **Audit:** security, admin, asset and ticket events are written in the same transaction as the change; passwords, hashes and tokens are never recorded.
- **Migrate command:** `migrate` applies pending EF Core migrations, then every post-migration step not yet in `maintenance_steps`, each in its own transaction with its record (a failed step changes nothing and runs again next time). Step `RecomputeCatalogNamesStep` recomputes `brands.normalized_name` and `asset_models.normalized_name` with `CatalogName.Normalize`, so keys no longer depend on the database `lc_ctype`; it writes in two passes (row-unique placeholder, then the final key) because a new key may equal another row's old key under the unique index. Output names the applied migrations; a failure prints `Migration failed: …` and exits 1, and compose then keeps `api` and `worker` stopped.
- **Timeline order:** timeline queries order by time, then id. `Guid.CreateVersion7` is random within one millisecond, so event ids come from `SequentialId` (monotonic within the process) and events written in the same instant keep their creation order.
- **Deployment (ADR-0024):** `tools/deploy.sh` checks for `deploy/.env` and the certificate pair, runs `tools/lint.sh` and `tools/test.sh` unless `--skip-gates`, refuses a working tree with uncommitted changes, builds both images on fresh base images (`docker build --pull`) tagged with the Git short hash and `latest`, records the hash in `deploy/.version`, pulls `postgres` and `nginx`, starts the stack and waits up to 180 s for `/api/v1/health` through nginx. `tools/docker-build.sh --allow-dirty` builds a `<hash>-dirty` test image and never moves `latest`. Every service's container log rotates (`json-file`, 5 files of 10 MB). `api` and `worker` start only after `migrate` exits 0; `api` reports healthy through `GET /api/v1/health`.
- **Backup (ADR-0025):** the `backup` service runs at `BACKUP_TIME` in `TZ`; `tools/backup.sh` runs one on demand. Dump, row counts and newest migration id come from one exported snapshot (`pg_export_snapshot` + `pg_dump --snapshot`), so the manifest describes exactly what the dump holds; the manifest also carries `dbSha256` (SHA-256 of `db.dump`) and `fileCount`. Archives are written under a temporary name, renamed when complete, mode 600; expired archives are deleted only after a successful run, and never by a safety backup (`BACKUP_SKIP_RETENTION=true`).
- **Restore (ADR-0025):** `tools/restore.sh <archive> [--force] [--no-safety-backup]` refuses before writing (exit 2 not an archive, a `db.dump` that does not match `dbSha256`, a missing `dbSha256` or a file count that differs from the manifest; 3 newer build than `migrate --print-latest`; 4 non-empty database without `--force`). With `--force` on a database that has tables it first takes a safety backup (`tools/backup.sh --safety`: one-off backup container, retention skipped so an expired archive being restored from the backup folder survives) and stops if that fails; a refusal restarts exactly the services that ran before; after writing it checks row counts against the manifest (exit 5), runs `migrate` and starts the stack. A failure while writing leaves the application stopped on purpose. `tools/restore-drill.sh` exercises the real scripts and images on two throw-away compose projects and writes `docs/release/restore-drill.md`.
- **Pilot seed:** `seed-pilot` (`tools/seed-pilot.sh`, `--compose` for a deployed stack) runs only in `Development` or `Pilot` and on a database without tickets. Through the application handlers it writes departments, a location tree, intake and field teams, 8 IT staff, 50 employees, 2 approvers, categories (including "ProteoSM Pilot"), request types, a device catalog, 500 assets, 2,000 tickets over 90 days, 20 articles, 60 changes, 150 standalone tasks, 50 problems (every problem state, linked incidents, a fixing change on resolved problems, an article on known errors) and 8 services (SAP, E-posta, VPN, Dosya sunucusu, Yazıcılar, İnternet, ERP mobil, Telefon) with an owner team and one to four assets each, set on about 30% of the tickets, every third change and every second problem from a random of their own (`--scale` multiplies, at most 10; fixed random seed, so the same scale gives the same data). Accounts use `@pilot.example.com` and one pilot password printed once. It closes the outbox rows it created, so seeded notifications are never sent; SLA breach notifications for open seeded tickets still follow later, so a pilot host runs with a relay that drops that domain or `EMAIL_MODE=Pickup` while only seed data exists. Child location names carry no parent prefix, so CSV import paths resolve them.
- **Performance measurement:** `tools/perf-measure.sh` times lists, searches, the workspace queue, every report (including the change, task and problem reports), the change calendar, the problem list, central search (also by a problem title word), a drill-down, synchronous Excel export and CSV preview/commit of 5,000 rows (one warm-up per operation, median and p95) and writes `docs/release/performance.md`; it refuses the development API port 5080 because the CSV commit writes 5,000 assets per run.
- **Acceptance evidence:** `docs/release/acceptance.md` maps each `proteosm.md` §20 criterion to tests, scripts or documents.
- **User guide:** `tools/guide-screenshots.sh` shoots the pages in `frontend/guide/manifest.ts` at 390×844 and 1280×800 from the seeded pilot database; `tools/build-user-guide.sh` builds `docs/user-guides/combined.md` and the A4 `combined.pdf` and checks anchors and images.
- **Name (ADR-0037, ADR-0043, ADR-0047):** the product is ProteoSM, shown as "ProteoSM by ProteONE" on the sign-in screen, in the side menus and in the footer of the default email texts. It was Proteone from November 2026 and TGYSM before. Data Protection keeps the former names (`Tgysm`, purposes `Proteone.EmailSettings`, `Proteone.MonitoringSecret`, `Proteone.LicenceKey`), the monitoring webhook headers keep `X-Proteone-*`, and the migration `ProteoneBrand` replaced TGYSM in email templates. The session and antiforgery cookies are `__Host-proteosm` and `__Host-proteosm-af`, so everyone signs in once after the move. Compose, database, user and volume names are `proteosm`; the `PROTEONE_*` environment variables are still read while the `PROTEOSM_*` ones are missing; `tools/deploy.sh` refuses to start a fresh stack beside a Proteone stack with data unless `--fresh-install` is given, and `tools/restore.sh` restores Proteone archives. The local storage key `proteone.sidebar.narrow` is unchanged. The migration `ProteoSMEmailDefaults` moved the default email texts to ProteoSM and added the footer line; an edited template is left alone. A Proteone installation moves by backup and restore (`docs/operations.md`); there is no upgrade path from a TGYSM installation.
- **Two entry pages (ADR-0038):** one build, `index.html` and `admin/index.html`; a link between the areas loads the page, sign-in returns to the admin page through the local `from` parameter.
